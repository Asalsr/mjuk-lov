# Mjuk Lov — Recipe Mini-App · Build Plan

> A real, shippable recipe app inside the existing Mjuk Lov Next.js site,
> with device-local personalization and an AI that "remembers" each user.
> Companion to `mjuk-lov-handbook.md`. **Last updated:** 2026-06-02.

---

## 1. Goal & scope

**Phase 1** — ship a public, bilingual recipe section at `/[lang]/recept` that:

- Shows dessert recipes with embedded YouTube technique videos (official iframe only).
- Auto-drafts an **EU 1169/2011 allergen + ingredient declaration** per recipe (AI-assisted, human-approved).
- **Personalizes via device-local storage**: each user's dietary profile/allergies, saved favorites + notes, cooking history, and their own recipes — stored in *their own browser*, no accounts.
- Has **one runtime AI feature** — a personal assistant ("what should I bake?", auto allergen-filtering) that reads the user's local profile and answers via a stateless server route.
- Is on-brand, fast, and SEO-friendly.

**Deferred to Phase 2** (see §16): user **accounts + cross-device sync**, a real **database backend (Supabase)**, server-side AI memory, shopping/checkout, DIY-kit QR companion, Persian/RTL.

---

## 2. Guiding principles

1. **AI is author-time by default; exactly one runtime AI feature.** Content (allergen labels, headnotes, translations) is generated by scripts at authoring time and served static — zero per-visitor cost. The single runtime feature (personal assistant) goes through a **stateless server route** (`app/api/ai`) so the API key stays server-side and never ships to the browser. It is rate-limited and stores nothing server-side.
2. **The AI's "memory" lives on the user's device.** Favorites, diet, history, and notes are stored in the browser and sent to the assistant as *context* per request. No database, no accounts — yet still "it knows me."
3. **Legal labels are drafts until a human approves them.** Hybrid engine (AI reasoning + deterministic safety-net + fixed wording), proven in `spike/ai-allergen.mjs`.
4. **Brand first.** Reuse the existing design system (Cormorant/Inter/Didact, palette, wax seal, noise texture).
5. **Original content only.** Embed others' YouTube videos; write our own notes. Never re-host video or scrape blog prose/photos.
6. **Build for the backend we don't have yet.** Both data layers (`lib/recipes`, `lib/userdata`) are storage-agnostic interfaces, so Phase 2's Supabase swap is a backend change, not a rewrite.
7. **Provider-agnostic AI.** Prototype on OpenAI, flip to Claude with one env var.

## 3. Architecture decisions

| Area | Decision | Why |
|---|---|---|
| Framework | **Next.js 16 App Router** (existing) | No new stack. *`params`/`searchParams` are Promises in this version — await them (verified in bundled docs).* |
| Recipe pages | **Server Components, statically generated (SSG)** via `generateStaticParams` | SEO + speed; recipes change rarely. |
| Recipe content | **Local typed files** `content/recipes/*.json`, validated by Zod, behind `lib/recipes` | Git as CMS; no DB in Phase 1; swappable for Supabase later. |
| **User data** | **Device-local** (localStorage/IndexedDB) behind `lib/userdata` interface | Personalization + AI memory with no backend, no accounts, minimal GDPR. Same interface → Supabase in Phase 2. |
| Author-time AI | Node scripts (`scripts/`) reusing the spike engine ported to TS | Zero runtime cost for content. |
| Runtime AI | **One stateless route** `app/api/ai/route.ts`; key in server env; rate-limited | Personalized assistant without leaking the key or storing data. |
| Locale | **Path-prefixed** `/[lang]/recept` (`sv` default, `en`) | Best SEO; proper `hreflang`. |
| Hosting | **Vercel** (existing) | Static pages + serverless route for the AI assistant. |

## 4. Data models

### 4a. Recipe — `content/recipes/<slug>.json` (Zod-validated)

```jsonc
{
  "slug": "tiramisu",
  "title":    { "sv": "Tiramisu", "en": "Tiramisu" },
  "headnote": { "sv": "...", "en": "..." },
  "servings": 8,
  "time": { "prepMin": 30, "totalMin": 240 },
  "youtubeId": "XXXXXXXXXXX",
  "ingredients": [ { "qty": "300 g", "item": { "sv": "savoiardi", "en": "ladyfingers" } } ],
  "steps":  [ { "sv": "...", "en": "..." } ],
  "notes":  { "sv": "...", "en": "..." },
  "allergens": {
    "codes": ["gluten", "egg", "milk", "sulphites"],
    "declaration": { "sv": "Innehåller: ...", "en": "Contains: ..." },
    "needsReview": [], "approvedBy": "saeedeh", "approvedAt": "2026-06-10"
  },
  "published": true
}
```

### 4b. User data — device-local, `lib/userdata` (same shape Phase 2 will sync to Supabase)

```ts
type UserData = {
  profile: {
    locale: "sv" | "en";
    diet: ("vegan" | "vegetarian" | "none")[];
    allergies: AllergenCode[];      // ⚠ health data — see GDPR note §11
  };
  favorites: string[];               // recipe slugs
  notes: Record<string, string>;     // slug -> personal note
  history: { slug: string; cookedAt: string }[];
  myRecipes: Recipe[];               // user's own recipes (IndexedDB)
};
```

`lib/userdata` exposes a storage-agnostic API (`getProfile`, `saveProfile`, `toggleFavorite`, `getNote`/`saveNote`, `logCooked`, `getHistory`, `addMyRecipe`, `exportAll`, `importAll`). localStorage for small data, IndexedDB for `myRecipes`. **`exportAll`/`importAll`** give the user a backup (mitigates "cleared browser = lost data") and become the migration path into an account in Phase 2.

## 6. AI: author-time toolchain + one runtime feature

**Author-time (free at runtime, key local):**
- **`npm run label -- tiramisu`** — hybrid engine writes a draft allergen label; human approves. *(Proven in spike.)*
- **`npm run import -- <url>`** *(stretch)* — extract a recipe draft from a YouTube/blog link.
- **`npm run translate -- <slug>`** *(stretch)* — fill missing sv/en fields in brand voice.

**Runtime (one feature, stateless, rate-limited):**
- **`POST /api/ai`** — body `{ question, userContext }`. The browser sends the user's local profile/favorites/history as `userContext`; the route adds a system prompt and calls the provider (key in server env), returns the answer. **Stores nothing.** Powers: "what should I bake for a nut-free birthday?", auto allergen-filtering of suggestions, and the adapt feature below.
- **Adapt a recipe → vegetarian / vegan.** A button on each recipe detail page sends the recipe to `/api/ai` and gets back suggested ingredient swaps (e.g. mascarpone → cashew/coconut mascarpone, eggs → aquafaba) for the chosen diet. The result then runs through the allergen engine so the adapted version gets its **own recomputed allergen draft** (milk/egg drop out). Output is a suggestion the user/author reviews — not auto-published.
  - **Guards:** simple per-IP rate limit + a max length, to cap cost/abuse on a public endpoint. Optionally cache answers to common questions.

## 11. Personalization, i18n & GDPR

- **i18n:** content carries both languages; the `lang` segment selects server-side. UI strings in `lib/i18n`.
- **Personalization:** Client Components read/write `lib/userdata`; AI assistant receives local context per request.
- ⚠️ **GDPR (important even device-local):** allergy data is **special-category health data (Art. 9)**. Storing it on the user's *own device* is light-touch, **but sending it to the AI provider is processing health data.** Therefore:
  - Show a clear **consent prompt before the assistant uses allergy/diet data**; let users use the app without it.
  - State in a short **privacy note** what's stored locally, that it never leaves their device except when they ask the assistant, and which AI provider processes it.
  - Keep `userContext` minimal — send only what the question needs.

## 16. Phase 2 — full backend (the confirmed next step)

> **Why accounts (rationale, user 2026-06-03):** the device-local "Made it" history,
> favorites and notes only live in one browser. A real **user page** (history of what
> they've made, saved cookbook) needs an identity to attach to — i.e. accounts. And the
> *same* account system powers **ordering and subscriptions**. So one Supabase auth = a
> personal recipe page **and** the commerce layer. Build identity once, use it for both.

When the brand launches / personalization proves valuable:

- **Supabase**: Auth (accounts) + Postgres + Row-Level Security + Storage.
- **Migrate device-local → account**: on first login, `importAll` pushes the user's local data into their row (upsert). Same `lib/userdata` interface, new backend — no UI rewrite.
- **Server-side AI memory**: durable, cross-device history; richer personalization than per-request context.
- **GDPR Art. 9 done properly**: explicit consent records, encryption, data-export & deletion (right to erasure), processor agreement with the AI vendor.
- **Shopping**: products + orders tables, **Stripe checkout** (handbook scopes `app/api/checkout`).
- **DIY-kit QR companion**: step-by-step video/illustration per kit.
- **Persian (RTL)** locale.
- **Personalized offers & discounts** (user 2026-06-03): use each user's profile + likes + cooking history to target offers and discount codes; ties into ordering/subscriptions and the AI assistant. Requires explicit **marketing consent** (GDPR) separate from the AI consent.

## 17b. Noted enhancements (captured 2026-06-02, not yet scheduled)

- **Richer / more practical detail pages.** User wants recipe pages to be more detailed and practical than the current first pass. Revisit content depth (step images, timings per step, equipment, tips, yield notes) in a later pass.
- **Ingredient unit conversion.** Let users convert measures (g ↔ oz, dl ↔ ml ↔ cups, °C ↔ °F). Requires a schema change: store quantities as structured `{ value, unit }` (not the current free-text `qty` string) plus an ingredient density table for weight↔volume. Client-side converter component on the detail page. Plan as its own milestone.

## 18. Risks

| Risk | Mitigation |
|---|---|
| Wrong allergen label (legal) | Human approval gate + Vitest tests + safety-net dict |
| GDPR — health data sent to AI | Consent prompt before using allergy data; privacy note; minimal context; proper Art. 9 handling in Phase 2 |
| User loses data (clears browser) | `exportAll`/`importAll` backup; sync in Phase 2 |
| Public `/api/ai` abused → cost | Rate limit + length cap + answer caching; monitor spend |
| Next 16 API differences | Verify against `node_modules/next/dist/docs` before each route/metadata task |
